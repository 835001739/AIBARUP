# AIBAR 设计文档

> 描述 AIBAR 的系统架构、模块设计、关键数据模型与本轮（会话内）已落地的优化决策。
> 配套文档：`docs/需求文档.md`（需求基线）、`docs/API_CONTRACT.md`（前后端接口契约）、`docs/OPTIMIZATION_REVIEW.md`（优化排查与修复记录）、`ACCEPTANCE.md`（验收报告）、`HARNESS.md`（工程规范）。

---

## 1. 系统架构概览

```
                         ┌─────────────────────────────┐
   浏览器 (本机)  ───────▶│  AIBAR  :8099  (Flask)       │
   static/index.html     │                             │
   (暗色工作室 UI)                                 │  app.py (装配 + 启动)        │
                         │   ├─ sync      bp  (M1-M4)  │
                         │   ├─ prompt    bp  (M6)     │
                         │   ├─ promptlib bp  (M7)     │
                         │   ├─ reverse    bp  (M9-M11)│
                         │   └─ comic     bp  (M12-M14)│
                         │        │                    │
                         │        ▼                    │
                         │  core/ (db/responses/      │
                         │         errors/logging/    │
                         │         textutil/imagemeta) │
                         │        │                    │
                         │        ▼                    │
                         │  SQLite  data/aibar.db      │
                         └──────────┬──────────────────┘
                                    │ HTTP /prompt · /view · /object_info
                                    ▼
                         ┌─────────────────────────────┐
                         │  ComfyUI  :8188             │
                         │  (conda comfyui 环境)        │
                         │  + AIBAR-Bridge 深链扩展     │
                         └─────────────────────────────┘
```

**设计原则**（来自 `HARNESS.md`）：
- `app.py` 只做装配（注册 Blueprint、全局错误处理器、CORS、页面路由）与启动（幂等迁移、种子导入、Provider 自检、同步线程拉起）；不含业务规则。
- 依赖严格单向：`config/core` ← `sync`/`prompt`/`promptlib` ← `reverse`；业务包之间不得互相 import，跨包能力经函数参数或 `core` 传递。
- 任何外部调用（HTTP / 文件 IO / ComfyUI）必须 `try/except` 且设超时；单子系统故障只降级该能力，绝不让应用起不来（启动每一步独立 try/except）。

## 2. 部署与运行

| 项 | 默认值 | 来源 |
|---|---|---|
| AIBAR 地址 | `127.0.0.1:8099` | `AIBAR_HOST` / `AIBAR_PORT` |
| ComfyUI 地址 | `127.0.0.1:8188` | `COMFYUI_HOST` / `COMFYUI_PORT` |
| 数据库 | `data/aibar.db`（SQLite，WAL 已开） | `AIBAR_DB` |
| 同步间隔 | 10s，自动开启 | `SYNC_INTERVAL` / `SYNC_AUTO` |
| 上传上限 | 20MB，TTL 24h | `REVERSE_UPLOAD_MAX_MB` / `REVERSE_UPLOAD_TTL_HOURS` |
| CORS 白名单 | 仅 ComfyUI 自身来源 | `CORS_ALLOWED_ORIGINS` |

**一键启动**：`./scripts/up.sh` 是启动编排入口，按「ComfyUI 先起（冷启动慢）、AIBAR 后起」顺序拉起两个服务，并把 `comfyui_bridge/AIBAR-Bridge` 同步进 ComfyUI 的 `custom_nodes/`。子命令：`start` / `stop` / `restart` / `status` / `open` / `bridge` / `logs`；`stop`/`restart` 可加 `--force` 连非本脚本启动的端口占用者一并结束（默认不杀，避免误伤）。

> 注：AIBAR 以 `debug=False, threaded=True` 运行，**无 reloader**；改 Python 需 `./scripts/up.sh restart --force`，改静态 JS/HTML 仅刷新页面即可。

## 3. 模块设计

### 3.1 同步引擎（M1–M4，`sync/`）

- **`comfyui_ctl.py`**：探测 ComfyUI 存活、设备、显存、argv；永不抛异常，降级为 `running:false`。`POST /api/comfyui/start` 后台拉起。
- **`scanner.py`**：扫描工作流目录、产出图目录、模型目录，基于内容哈希做增量判定。
- **`parser.py`**：把工作流 JSON 解析为结构化卡片（节点数、节点类型、正 / 负提示词预览）。
- **`watcher.py`**：后台轮询线程（`SYNC_INTERVAL`），首跑种子策略快速出图；首跑失败只记告警（已加 `_FakeThreading` 测试桩避免真实线程）。
- **`workflow_convert.py`**（M2 增强）：把 ComfyUI UI 格式工作流转换为 API `prompt` 图，复用 `/object_info` 判定挂件与连线；提交 `POST /prompt` 出图。
- **`graph_prompt.py`**：工作流图结构可视化数据（`GET /graph`）。
- **`paths.py` / `comfyui_link.py`**：深链「在 ComfyUI 编辑器中打开」；路径穿越防护收敛到 `safe_join()`（拒绝 `..` / 绝对路径 / 盘符，并用 `is_relative_to` 做边界判断）。

### 3.2 提示词工作台（M6，`prompt/`）

- **`library.py`**：模型档案（profile）定义——区分 `supports_negative`、`supports_weight`；维度（dimension）与场景模板。
- **`engine.py`**：确定性扩写引擎——按 profile 格式化正 / 负向，分维度产出段落，做去重与互斥检测，产出 `warnings`。同输入同输出。
- **`providers.py`**：外部 / AI 语义扩写 Provider；失败安全回退到 rules 引擎，日志不泄露 key / endpoint。
- **`routes.py`**：扩写与历史接口。

### 3.3 多模态精品词库（M7，`promptlib/`）

- **`entries.py`**：词条 CRUD + `get_facets()` 渐进分面（仅返回当前筛选条件下有数据的层级）。
- **`learning.py`**：生成后自动学习——把高置信度片段直接入库，低置信度进 `prompt_candidates` 待审核；近重复检测（`_find_near_duplicate`）。
- **`routes.py`**：词条与候选审核接口（含本次补齐的 POST/PATCH/DELETE 写操作）。

### 3.4 图片反推与 Provider 中心（M9–M11，`reverse/`）

- **`service.py`**：反推管线编排——上传引用 → 读图 → 元数据恢复 / 视觉模型 → 结构化结果 → 入库；任务真实阶段写库（`_set_stage`），支持同步 / 异步。
- **`schema.py`**：结构化结果校验（`validate_structured_result`）。
- **`uploads.py`**：上传缓存管理（内容哈希去重、`cleanup_expired` 后台清理）；校验真实图片内容，拒绝动画 / 损坏文件。
- **`comfyui_client.py`**：同源代理 ComfyUI `/view`，渲染产出图。
- **`providers/`**：Provider 注册中心（`registry.py`）+ 实现：`metadata`（原始提示词恢复）、`comfyui_blip`（本地 BLIP）、`qwen3vl`（本地 Qwen3-VL 8B/4B，经 `AILab_QwenVL_GGUF` 节点）、`joycaption`（gated）、`openai_compatible`（外部视觉）。

### 3.5 ComfyUI 桥梁扩展（`comfyui_bridge/AIBAR-Bridge`）

前端深链扩展，使「在 ComfyUI 中打开并载入工作流 + 提示词」「用 ComfyUI 出图」按钮可用；由 `up.sh` 同步进 ComfyUI `custom_nodes/`。

### 3.6 漫画工作室（M12，`comic/`）

- **`routes.py`**：Blueprint `comic`，`url_prefix="/api/comic"`。项目 / 章节 / 分镜页的全套 CRUD，以及出图动作（`generate` / `regenerate` / 整章 / 整本 `generate`）、队列查看与取消、产出图同源代理。统一 `AIBARError` + 本地 `@bp.errorhandler`；请求体经 `_json_body()` 校验为 dict，否则 `invalid_input`。
- **`service.py`**：层级 CRUD 与出图编排。核心职责：
  - 维护 `project → chapter → page` 三层结构与级联删除（删项目清章节 + 页 + job；删章节清页 + job）。
  - `_enqueue(page_id)`：把页置 `queued`，写 `comic_jobs`（`status=queued`）；若页已 `generating` 则拒绝再入队。
  - `regenerate_page(page_id)`：无视当前状态重新入队（大工作流完成后单图重生成的核心入口）。
  - `enqueue_chapter` / `enqueue_project`：批量把未 `done`（或指定条件）的页入队。
  - `list_jobs(project_id, status)`、`cancel_job(job_id)`：取消仅把排队中页重置 `pending`，不动已 `done` 页。
  - 状态枚举集中于常量：`_PROJECT_STATUS={"draft","production","done"}`、`_PAGE_STATUS={"pending","queued","generating","done","failed"}`。
- **`runner.py`**：后台出图 worker（`ComicWorker` + `run_job`），由 `app.py::bootstrap()` 的 `_start_comic_worker()` 拉起为守护线程（失败只记告警，不阻塞启动）。单任务流程：
  1. `build_api_graph()`：读取页关联的 `workflow_filename`（经 `sync.paths.safe_join` 取 ComfyUI 工作流目录），用 `sync.workflow_convert.convert_text` 把 UI 格式转 API prompt 图；
  2. `_inject_prompt(graph, page)`：把 `prompt_text` / `negative_text` / `seed` 注入对应文本编码节点。节点识别做**三层兜底**：先看节点 `title`（`_NEGATIVE_HINTS` 含 `negative/负面/ugly/blurry/低质量/模糊/畸形…`）→ 再看节点已有内容是否本身就是负面词 → 最后才按「第一个文本节点正向、第二个负向」的位置兜底；正向节点缺失时退化到首节点，只有 1 个节点时不强行写负面。这样自定义 / 导出顺序不同的工作流也能正确注入，不再依赖脆弱的节点顺序假设。
  3. 经 `reverse.comfyui_client.submit_prompt` 提交 ComfyUI `POST /prompt`，`wait_history(timeout=180.0)` 轮询；
  4. `_first_image(history)` → `_download_output_bytes()` → `_save_output()`：取首张成图字节，按 `sha256[:16]` 落盘 `comic_outputs/<project>/<chapter>/<page>_<hash>.png`（库内仅存相对 `DATA_DIR` 的路径）；写盘前先 `dest_dir.glob("{page_id}_*.png")` 删除该页的**旧产出**（重出图不再堆积历史文件）；写回页 `status=done` + `output_path`，job 置 `done`；失败则页置 `failed` + job `failed` + `error_code`。
- **`__init__.py`**：`get_worker()` 懒加载单例、`start_worker()` 启守护线程，失败安全。
- **`styles.py`**：分镜工作流「出图风格」预设（保证整部漫画每一集、每一页风格统一）。纯数据 + 纯函数、可离线单测：`STYLE_PRESETS` 注册 9 种风格（`none` / `japanese_manga` / `shinkai` / `american_comic` / `ink_wash` / `watercolor` / `cyberpunk` / `pixel_art` / `realistic`），每种给出中文 `label`/`desc` 与面向模型的**英文** `positive`（风格描述词）/ `negative`（排除项）；`normalize_style(value, fallback)` 把任何非法输入收敛到合法预设（绝不抛异常），`is_valid_style` 用于区分「传入非法值」与「未传值」；`apply_style(positive, negative, style, max_len)` 在正面提示词**末尾**追加该风格的统一描述词、在负面提示词合并统一排除项，**幂等**（已含则不重复追加），超长截断时 `_truncate_keep_tail` 优先保留风格词（风格统一优先于剧情细节）。生成链路对**每一集的每一页**调用同一个 `apply_style`，这是「风格统一」的唯一实现点。
- **`skill_import.py`**：Skill → 漫画工作流的「可复用导入器」（支撑「任意 skill 流程 → 本项目能力」）。`parse_skill_md(text)` 解析 frontmatter + `## 段落` + 编号步骤；`_should_skip(title)` 按大小写 + 去括号前缀跳过说明性段落；`ensure_flux_workflow()` 把 FLUX.2 最小化 13 节点 API 工作流（`flux2_storyboard_aibar.json`）落盘到 ComfyUI 工作流目录；`import_skill(text, title, workflow_filename)` 创建 `project → chapters → pages` 三层并复用 `service` 的既有 CRUD（不新增表）。种子注入在 `runner._inject_prompt` 兼容 `seed` 与 FLUX.2 的 `noise_seed` 两种键。
- **`storyboard.py`**：漫画分镜工作流（世界观 + 剧情摘要 → 自动分集出图）。`plan_episodes(worldview, plot_summary, provider)` 确定性地把剧情拆成「集」：按「第N集 / 第N话 / EPn / 数字.数字 / （数字）」标记或空行分段，单段落内联编号（「1. a 2. b」）也拆，无标记则整体作一集（上限 24）；`provider="openai_compatible"` 且 `AI_PROVIDER_*` 启用时尝试用 LLM 拆分，任何失败回退规则引擎。`generate_storyboard(project_id, ..., pages_per_chapter, style, mode)` 先可选写回世界观/剧情摘要/**出图风格**（仅当 `style` 为合法预设时写回，非法值不污染项目设置），再按 `mode` 决定处理方式后逐集建「章节 + N 张分镜页」：
  - **生成模式 `mode`**（`append` 默认 / `rebuild`）：`rebuild` 先遍历 `service.list_chapters` 逐个 `delete_chapter`（级联删分镜页与 job），并把「已清理 N 个旧章节」记入 `warnings`，再重新生成 —— 解决反复点「一键生成」叠加出多个「第1集」的问题；非法取值抛 `AIBARError("invalid_input")`。
  - `split_scene_into_beats(scene, n)` 把每集剧情转换为 N 个画面描述，返回 `[{"beat", "shot"}]`：`_split_sentences` 按句切分，句数足够则均匀取样覆盖首尾，**句数不足则循环取句** `sentences[i % len(sentences)]`（旧实现是复制末句，导致整集画面雷同），并按页序轮换 `_SHOT_FRAMING` 给每页一个独立景别（远景，建立镜头 / 中景 / 近景 / …）。`_split_scene_into_beats` 保留为兼容包装（返回 `beat+shot` 拼好的字符串列表）。
  - 每个画面描述经 `prompt.providers.expand`（规则优先、AI 可选）扩写，扩写结果**原文**存进 `base_prompt` / `base_negative`，景别存进 `shot_note` —— 这三列是「提示词可重建」的原料，保存的是**注入角色锚点之前、追加风格词之前**的形态。
  - 装配统一走 **`compose_page_texts(base_prompt, base_negative, shot, chars, setting, style, base_seed, project_id, chapter_id, page_idx)`**：拼装顺序为「世界观设定 → 角色锚点（`compose_page_prompt`）→ 画面描述 → 景别」，负面词合并角色排除项，再经 `styles.apply_style` **按出图风格统一规范**（每一页完全一致），最后由 `characters.derive_seed` 派生确定性种子。这个函数是**纯函数**，且是首次生成与后续重刷的**唯一**装配入口 —— 两条路径不可能出现逻辑漂移。
  - 角色命中用 `characters.select_page_characters(beat, chars)`（文本命中 ∪ 主角）而不是单纯的名字匹配；装配结果写入 `prompt_text`/`negative_text`/`seed` 并自动入队；项目未设默认工作流时经 `skill_import.ensure_flux_workflow()` 自动写入 FLUX.2 工作流并设为默认，实现零配置出图。返回体带 `mode` 与 `removed_chapters`。复用 `service` 既有 CRUD，不新增表。
  - **`refresh_project_prompts(project_id, style=None, requeue="failed")`**：只重跑装配层的「重刷」入口。遍历项目全部章节的分镜页，取 `base_prompt or prompt_text`（历史页兜底）作原料，重算 `prompt_text`/`negative_text`/`seed`，仅在**结果与库中不同**时写回并计入 `changed`（因此天然幂等）；`style` 为空表示沿用项目当前风格，传值则整本换风格（同样只接受合法预设）；`requeue` ∈ `failed`（默认，只重排失败页）/`all`/`none`，非法值抛 `invalid_input`。返回 `{updated, changed, enqueued, style, style_label, characters, character_names, requeue, warnings}`。
- **`groups.py`**：M14 · 组图（同一人物的连贯动作序列 + GIF 式连播）。不扩漫画分镜表，独立两张表 `shot_groups` + `shot_frames`（详见 §4）。核心约束：
  - **「强制预设提示词」的执行**：preset_prefix/preset_suffix/preset_negative 由组图统一提供，帧只存 `action_text`；`refresh_prompts` 一键按当前预设**覆盖全部帧**——单帧改不动提示词，这是连播时人物不漂、画风不跳的根本保障。
  - **提示词拼装顺序**：`[人物锚点] → [一致性指令] → [preset_prefix] → [action_text] → [preset_suffix]`（锚点前置继承 M12 已验证的结论）。
  - **种子策略**：`seed = (base_seed + order_idx * seed_step) % 2**31-1`；`seed_step=0`（默认）= 全部帧同一种子，是「连贯动作」的关键——同种子 + 不同提示词，模型保留人物与构图只改动作，连播起来像同一人做连续动作；调大 step 可拉远动作幅度但脸开始漂。
  - **`resolve_anchor(group)`**：演员锚点 → 角色卡锚点 → `anchor_override`，**不存快照**——改演员定妆后调一次 `refresh_prompts`，全部帧同步更新。
  - **串行出图**（`generate_group`）：ComfyUI 单卡排队，并发只会互相抢显存。`_RUNNING` 集合 + `_STATE_LOCK` 保证同一组图不会被两个 worker 抢；单帧 `regenerate_frame` 让位整组出图（防两线程抢同一张卡）。
  - **状态机**（`_sync_counts`）：`idle / generating / ready / partial / failed`。**出图期间用 `_RUNNING` 强制压住 `generating`**——worker 每帧重算时其他帧还是 pending，纯按计数会得出 `partial`，前端轮询看到它会误判「出完了」而停掉进度条。
  - **落盘**（`_save_frame_image`）：先写新图、再清旧图（沿用 M13 沉淀的 `core.fileops.purge_stale` + `BASICException` 全兜）；新文件名 `<frame_id>_<sha256[:16]>.png`，目录 `data/comic_outputs/shotgroups/<group_id>/`。
  - **`playlist(group_id)`**：只返回 `status='done'` 的帧，按 `order_idx` 排序；URL 优先 `/static/gallery/...`（图库副本），图库登记失败退回 `/api/comic/output/...`；前端全量预加载后逐帧切换 `src`（不闪）。
- **`recovery.py::reap_stale_frames`**（M14 扩展）：与 `reap_stale_jobs` 同模式。找出 `status='generation' AND updated_at <= now-15min` 的帧，复位为 `failed`（带可读中文原因）并重算所属组图聚合状态。**不复位为 pending**：用户已经看过界面，偷偷重跑会覆盖认知，让 UI 显式提示「上次进程退出时中断，请在「动作帧」里点「重生成」」。手动触发 `POST /api/comic/maintenance/frames-reap`。
- **`characters.py`**：人物一致性（角色卡 / 人物锚点 / 确定性种子），是「同一个人每页长得一样」的唯一实现点。纯数据 + 纯函数、可离线单测。
  - 抽取 `extract_candidates(*texts, limit)`：称谓词典直击 + 「XX说/道/问」式人名捕获 + 英文人名 + 「称谓 + 人名」组合捕获；`_strip_name` 削掉粘连的动词/虚词尾巴（`阿岚说`→`阿岚`、`少女苏叶点头`→`苏叶`）与称谓前缀（`少女苏叶`→`苏叶`），`_clean_name` 再用 `_NAME_FORBIDDEN`（助词/量词/动作字）与 `_NON_NAME_WORDS`（「沉默」「微笑」等高频非人名双字词）拦掉误抽取；已被完整人名吸收的裸称谓（「少年阿岚」里的「少年」）记录在 `absorbed` 并被剔除，避免同一角色被拆成两张卡。
    - 人名捕获的字集 `_SPEECH_VERB_CHARS` 已从 ~22 个「言说动词」扩充到约 200 字（言说/表情、视线/头部、身体/移动、手部、心理/状态 + 高频叙事虚词 `在是有于为把被将使对向给从用`），`_SPEECH_RE` 由该字集动态编译 —— 否则「阿岚离开家乡，走进雾气弥漫的森林」这类**纯叙事句**抽不出任何角色。「称谓 + 人名」分支会跳过紧跟动词的组合（`引路人递给他` 不抽出「引路人递」）。
    - 排序 `ranked = sorted(counts.items(), key=(-频次, 首次出场位置, -长度, 字典序))`：`first_pos` 在 `_bump` 时记录，用于同频次时让**先登场**的角色排第一（= 默认主角），避免「引路人」这类被多条规则命中的称谓词挤掉真正的第一主角「阿岚」。
  - 锚点 `build_character_anchor(char)`：按固定顺序（名字 → 外貌 → 服装 → 配色）只拼非空字段，因此同一角色在**任何一页**得到的锚点**逐字相同**。
  - 组装 `compose_page_prompt(scene, chars, shot, setting)`：**世界观设定 → 角色锚点 → 画面描述 → 镜头景别**；锚点放在场景之前是因为图像模型对提示词靠前的描述权重更高；纯名字锚点且场景已提到时跳过，避免「少年，少年离开家乡」这类啰嗦提示词。
  - 种子 `derive_seed(base_seed, project_id, chapter_id, page_idx, key)`：SHA-256 派生后取模 `2^31-1`；`key` 取 `anchor_key(hits)`（角色名排序拼接），于是同一角色组合在同一位置永远得到同一颗种子 —— 跨页由 `page_idx` 拉开差异，重跑可复现。
  - **主角贯穿** `is_main(char)` / `select_page_characters(text, characters, include_main=True)`：`is_main` 容错解析 `bool/int/"1"/"true"/"yes"/"on"`；`select_page_characters` 取「文本命中 ∪ 主角」的并集，去重键为 `id`（无 id 时回退规范化名字，使内存中的临时卡在单测里也能正确去重），返回顺序**始终按角色卡顺序**（保证锚点拼接顺序稳定 → 种子与提示词都稳定）。这是「主角在过场页也不换脸」的实现点。`service.create_character` 让**首张卡默认主角**（`fallback=not existing`），`update_character` 用原值兜底，未传 `is_main` 的更新不会误清主角标记。
  - 剧本清洗 `_strip_leading_marks`（在 `storyboard.py`）：去掉集标记后残留的分隔标点（`第1集：少年…` → `少年…`），避免提示词里出现「锚点，：少年…」。
- **`diagnostics.py`**：ComfyUI 衔接诊断。`ERROR_TEXT` 把 ~23 个错误码映射成中文可读文案（`human_error(code, message)`，未知码回退原始 message）；`probe_comfyui(timeout)` 探测在线状态与耗时（任何异常一律降级为 `online:false`，绝不抛给路由层）；`workflow_report(filename, check_nodes)` 检查工作流文件存在性、节点数、`class_types` 与缺失节点（复用 `runner._workflow_file` 的 `safe_join` 路径穿越防护）；`precheck(project_id, check_nodes)` 汇总为 `{ready, comfyui, workflow, queue, hints}` 并给出中文建议。
- **重试与可读错误**（`runner.py`）：`MAX_ATTEMPTS=3`，`RETRYABLE_CODES` 覆盖 `comfyui_offline`/`comfyui_timeout`/`submit_failed`/`wait_failed`/`timeout`/`download_failed`，按 `RETRY_BACKOFF_SECONDS` 退避；重试时任务回到 `queued` 且 `stage='retry_wait'`、`next_retry_at` 指向未来，worker 取任务时只捞 `next_retry_at <= now` 的；`_mark_failed` 同时把中文文案写入 `comic_jobs.error_message` 与 `comic_pages.error_message`。
- **进度聚合**（`service.project_progress`）：纯数据库聚合（不访问网络），产出各状态计数、完成百分比、章节级进度、当前生成中页、最近失败与失败原因分布；ComfyUI 在线状态由路由层合并，探测失败不影响进度数据（失败不拖慢、不报错）。
- **剩余时间预估**（`service._avg_job_seconds`）：取该项目最近 `sample=5` 条 `finished_at - created_at` 的均值（跳过缺失字段、≤0 与 ≥3600s 的异常样本），`project_progress` 据此输出 `avg_job_seconds` 与 `eta_seconds = round(均速 × (queued_jobs + 正在出图 ? 1 : 0))`；无样本或队列为空时为 `0`，前端只在 `eta_seconds > 0` 时渲染 ETA 文案 —— 不猜、不显示无依据的数字。
- **依赖方向**：`comic/` 复用 `sync.paths.safe_join`、`sync.workflow_convert.convert_text`、`sync.comfyui_link`、`reverse.comfyui_client`——均为上游包能力经函数调用，未违反单向依赖（`config/core` ← `sync`/`prompt`/`promptlib` ← `reverse`；`comic` 作为新增业务包同样只依赖上游与 `core`）。

- **`flux2.py`**（M17）：FLUX.2 [klein] 结构控制工作流（ComfyUI API 格式）。与 M14 关系：「姿势可控出图」的能力升级版——从「SDXL+ControlNet+IPAdapter 三件套」换成「Klein 4B 单模型多参考图编辑」，少两个权重、节点拓扑从 15+ 砍到 21（含两条 ReferenceLatent 链），结构控制效果来自 BFL 官方为 Klein 训练的多参考图原生机制（`comfy_extras/nodes_edit_model.py::ReferenceLatent`），不是 ControlNet patch 注入。

  - **依赖清单**（已在部署的 ComfyUI v0.30.0 上 object_info 实测）：
    - 核心节点：`UNETLoader` / `CLIPLoader(type=flux2)` / `VAELoader` / `EmptyFlux2LatentImage` / `Flux2Scheduler` / `ReferenceLatent` / `VAEEncode` / `VAEDecode` / `CFGGuider` / `BasicGuider` / `KSamplerSelect` / `RandomNoise` / `SamplerCustomAdvanced` / `CLIPTextEncode` / `LoadImage` / `SaveImage`；
    - 模型三件套（已在本机）：`models/diffusion_models/flux-2-klein-4b.safetensors`（7.8GB）/ `models/text_encoders/qwen_3_4b.safetensors`（8GB）/ `models/vae/flux2-vae.safetensors`（0.3GB）；
    - 预处理器（`comfyui_controlnet_aux` 已装）：`DWPreprocessor`（DWPose）/ `Canny` / `DepthAnything`——用户在前端可勾选「出图前先用 DWPose 抽骨架」，骨架图作为 `control_image` 进入第二条 ReferenceLatent 链。
  - **节点拓扑**（21 节点，参考 `comic/pose.py::build_pose_workflow` 编号习惯）：
    - 1-3：模型加载（`UNETLoader` 4B 蒸馏版 / `CLIPLoader(qwen3_4b, type=flux2)` / `VAELoader(flux2-vae)`）；
    - 4-5：正负提示词（distilled 版 CFG=1.0，负向可留空）；
    - 6-9：**外观参考链**（`LoadImage` + `VAEEncode` + 两条 `ReferenceLatent` 分别挂正/负 conditioning）；
    - 10-13：**结构控制链**（同上，挂在前链输出之后 → 实现"参考图先锁外观，结构图后锁姿态"的两段式控制）；
    - 14-15：空 latent + `Flux2Scheduler`；
    - 16-19：采样（`CFGGuider(cfg=1)` 或 `BasicGuider`，配 `KSamplerSelect(euler)` + `RandomNoise` + `SamplerCustomAdvanced`）；
    - 20-21：解码 + 保存。
  - **关键决策**：
    - **为什么不是"真 ControlNet"**：`comfy/controlnet.py` 只到 `ControlNetFlux`（Flux1 架构），截至 2026-09-08 上游 `origin/master` 仍未加 Flux2 ControlNet；社区唯一的 Klein 真 ControlNet（`DiffSynth-Studio/Template-KleinBase4B-ControlNet`）是 DiffSynth 生态，需要 24-40GB CUDA GPU + `klein-base-4B`，无 ComfyUI 节点。
    - **本机（M3 Pro 36GB / 磁盘剩 28GB）的现实约束**：FLUX.2-dev bf16 23.8GB 装不下、跑不动；fp8 在 MPS 上不支持 → **只能走 Klein + ReferenceLatent 路线**（零下载、零安装、零额外权重）。
    - **效果验证**：实测同一 prompt「a fluffy white dog, sitting, on a wooden floor」加 vs 不加猫图参考 → 不加生成白色比熊犬，加猫图生成**白色长毛猫**（坐姿、窗台构图、阳光方向、木地板**完全复刻**参考图），证明 ReferenceLatent 不仅参考外观，更在结构/光照/构图层级生效——这就是 BFL Klein 替代三件套的"魔法"。
    - **采样默认值**：蒸馏版 4 步 / CFG=1.0 / sampler=euler（`Flux2Scheduler` 自动算 sigmas）。基础版走 50 步 / CFG=4.0 时需切换 `unet_name` 到 `flux-2-klein-base-4b` 并调整 `steps/cfg`。
    - **前端深链兼容**：`comic/workflow_ui.py::api_to_ui_graph` 自动 API→UI 转换，`sync/comfyui_link.build_editor_link_graph` 生成 ComfyUI 编辑器深链接——AIBAR-Bridge 的 `loadGraphData` 可直接消费。
  - **`ensure_flux2_workflow(...)`**：与 `comic.pose.ensure_pose_workflow` 同款——落盘 `user/default/workflows/aibar_flux2_structural.json`，幂等覆盖；两图都留空时自动扫描 ComfyUI `input/` 取首张 PNG 作参考图，保证落盘文件是 17 节点完整链（防回归测试 `test_ensure_flux2_workflow_auto_picks_reference`）。
  - **不引入新表 / 不动 schema**——纯工作流生成器，状态仍由 ComfyUI 自己维护。
  - **视频转绘集成**（M17→M16）：同一帧可二选一打开 ComfyUI 编辑器，UI 上**两个按钮并列**（SDXL 姿态链路 / FLUX.2 Klein 结构控制链路）。
    - 后端复用 `_prepare_frame_workflow_inputs(job_id, order_idx)` 上传参考图 + 骨架图到 ComfyUI input（与 `generate` 同一套「已登记文件名优先，否则上传一次」逻辑）；
    - 路由 `frame_flux2_workflow_graph` 返回 UI 格式工作流 JSON（`Cache-Control: no-store`），`frame_flux2_editor_link` 返回 ComfyUI 深链接（`mode=graph, target=4`，与姿态工作流的 `target=9` 区分）；
    - 取样参数走 Klein 蒸馏版默认（4 步 / CFG=1.0 / 1024×1024），**不继承**任务的 SDXL 参数（28 步 / CFG 6.5 / 896×1152）——把 SDXL 调参灌进 Klein 会出废图。
    - 深链接的 `target="4"` 对应 `build_flux2_workflow` 中正向 CLIPTextEncode 节点（姿态链路是 `target="9"`），由 `sync/comfyui_link.build_editor_link_graph` 一并写入。
  - **`build_flux2_pose_workflow(...)`**（M17.3，「姿势参考 + 人物一致」）：`character_images: Sequence[str]` 支持**多条人物参考链**，外加一条姿势链，解决「同一个角色跨帧换姿势」的场景。
    - **链式构造**：每条参考链 = `LoadImage` → `VAEEncode` → `ReferenceLatent(+)` → `ReferenceLatent(-)`（4 节点），正负 conditioning 各挂一条以保证正负两侧都吃到参考；
    - **节点 ID 分配**：主干占 1-5 / 14-21（13 节点，与 `build_flux2_workflow` 完全同构）；人物链从 `CHARACTER_REF_ID_BASE = 100` 起、**步长 4**（第 n 条占 `100+4n` ~ `100+4n+3`）——起始值刻意避让旧 builder 的 6-13，两套图不冲突；姿势链**追加在所有人物链之后**，保证「先锁人、后锁姿势」的顺序语义；
    - **`_add_reference(graph, image, pos_ref, neg_ref, base, title, vae_node)`**：单条链构造抽成公共 helper，`build_flux2_workflow` 重构后也走它（原 6-13 节点 id 由测试钉死，重构零回归）；
    - **`MAX_CHARACTER_REFS = 3`**：人物链上限。据 `/object_info` 实测，`ReferenceLatent` 的 `input` 只有 `required.conditioning` 与 `optional.latent`，**没有任何权重/强度参数** → 「这张参考图有多重要」**只能靠重复次数表达**（`character_images=[a,a,a]` 即权重 ×3）。超过 3 条链后注意力被参考图吃满，出图会「贴」参考图、失去变化，故设上限；
    - **`ensure_flux2_pose_workflow(...)`**：幂等落盘 `user/default/workflows/aibar_flux2_pose_consistent.json`；参数全空时自动扫 `input/` 下前两张 PNG（第 1 张当人设、第 2 张当姿势）；永不抛异常（`except Exception` 降级返回 `None`），避免拖垮调用方。
  - **M17.3 实测结论（重要，影响选型）**：同人设图 ×2 + 同 seed(12345) + 同提示词，只换 DWPose 骨架图，1024×1024 / 4 步 / CFG 1.0 出图后做像素级比对：

    | 对比 | 输入图差异 | 出图 MAD | >16 灰阶像素占比 | 判定 |
    |---|---|---|---|---|
    | 骨架 A vs 骨架 B | 5.73 | 1.97 | 3.3% | ❌ 输出差 ≪ 输入差 ⇒ 没跟随 |
    | 真实帧 A vs 真实帧 B | 25.98 | 3.33 | 2.6% | ❌ 输入差 26 / 输出差 3.3 ⇒ 同样没跟随 |
    | 有骨架 vs 无骨架 | — | 9.67 | 11.5% | ⚠️ 仅"多一条参考链"的整体扰动 |
    | 骨架 vs 真实帧（都当姿势参考） | 52.63 | 66.73 | 89.4% | ⚠️ 整张图被拖向那张照片 |

    与人设参考图的平均色差：骨架 / 无姿势 **1.24~1.36**（✅ 人物保住）；真实帧 **59.5~60.6**（❌ 人物丢失）。

    **结论**：`ReferenceLatent` 是**外观 / 整体构图迁移**机制，**不是** ControlNet —— 姿势参考基本被忽略；且用真实照片当姿势参考比用骨架**更糟**（出图被整体拖向照片，人物一致性同时丢失）。
    ⇒ Klein 路线可可靠做到**人物一致**，做不到**严格姿势控制**；后者走 M14（SDXL + ControlNet-Union openpose，真 ControlNet，骨架图原样吃）。本函数定位修正为「同人物稳定续写 / 分镜」，`pose_image` 的语义降级为"构图参考"而非"动作控制"。
  - **M14 姿势链路复核（2026-09-08，为验证上面的结论而做）**：`comic/pose.py::build_pose_workflow` 即 SDXL + ControlNet-Union openpose 链路，两个变体：
    - **锁脸 + 控姿（15 节点）**：`CheckpointLoaderSimple` + `CLIPVisionLoader` / `IPAdapterUnifiedLoaderFaceID` / `IPAdapterFaceID`（锁脸）+ `ControlNetLoader` / `SetUnionControlNetType(type=openpose)` / `ControlNetApplyAdvanced`（控姿，strength 0.9、0.0-1.0 全程）+ `KSampler`；
    - **纯 openpose 控姿（11 节点）**：`reference_image` 留空即跳过整条 IPAdapter 链（省 3 个节点与一次 insightface 人脸检测）。
    - **关键实现细节 / 坑**：`ensure_pose_workflow(..., filename=POSE_OPENPOSE_FILENAME, auto_fill=False)` —— `auto_fill` 默认 True 会在图像留空时自动扫 `input/aibar_poses/` 补齐，**导致想落「纯控姿」版却被补成 15 节点锁脸版**。故新增 `auto_fill` 开关（默认 True 保持向后兼容），并由 `test_ensure_pose_workflow_auto_fill_false_keeps_pure_openpose` 双向钉死（开→15 节点、关→11 节点）。
    - **实测对比（同一对骨架输入 pose_0000 / pose_0002，输入差异 MAD=5.73，同 seed 12345）**：

      | 链路 | 出图 MAD | >16 灰阶像素占比 | 判定 |
      |---|---|---|---|
      | SDXL + ControlNet-Union openpose | **50.28** | 72.8% | ✅ 姿势真驱动出图 |
      | FLUX.2 Klein + ReferenceLatent | 1.97 | 3.3% | ❌ 几乎无响应 |

      差一个数量级，证实「真 ControlNet 与注意力迁移参考」在姿势控制上是两回事。
    - **校验姿势不能用 DWPose 反向抽骨架**：实测 DWPreprocessor（`yolox_l.onnx`，真实人像训练）在本项目动漫风出图上**完全检不出人**——连参考图 `actor_ref.png` 本身都抽不出骨架（输出纯黑 stddev=0）。对照实验确认是检测器局限而非出图异常（出图 stddev 42~64，内容正常）。自动校验需换检测器或改用人像照片，当前只能肉眼判。

## 5. 本轮落地的关键设计决策与优化

> 以下四项已修复并补回归测试（详见 `docs/OPTIMIZATION_REVIEW.md`）。

### 5.1 错误处理一致性（P1-5 / P1-9）

- **问题**：`core/errors.py` 已定义但零调用的 `not_found()` / `unavailable()` 工厂函数未强制启用，`not_found` 偶发落到 400、`provider_unavailable` 在 400 与 503 间摇摆；`reverse/uploads.py` 把**所有**异常统一报 `invalid_image`(415)，程序 bug 被伪装成用户上传错误（吞异常掩真实故障）。
- **修复**：
  - 强制使用 `not_found()`（→404）、`unavailable()`（→503）工厂，统一状态码语义（实测 `not_found`→404、`invalid_input`→400、`provider_unavailable`→503）。
  - `reverse/uploads.py` 区分「可预期错误」（用户输入 ⇒ 415）与「程序缺陷」（⇒ 500 + 记 `type(exc).__name__`，保留异常链）：
    ```python
    owned: Path | None = tmp_path
    try:
        ... # validate -> os.replace(tmp_path, dest) -> owned = dest
    except AIBARError:
        _discard(owned); raise
    except _EXPECTED_IMAGE_ERRORS as exc:
        _discard(owned); raise AIBARError("invalid_image", ..., 415) from exc
    except Exception as exc:
        _discard(owned)
        _LOGGER.error("reverse_upload_internal_error error_type=%s", type(exc).__name__)
        raise AIBARError("internal_error", "上传处理失败，请稍后重试", 500) from exc
    ```
  - **真实 bug 修复**：dedup 命中后 `owned=None`（共享文件不删）；原先 `os.replace` 后 `tmp_path` 已消失却仍 `_unlink(tmp_path)`，导致异常时留下永久孤儿文件——已修。
- **验证**：`tests/py/test_error_handling.py`（21 项）覆盖状态码语义、写失败→500（非 415）、写失败不留临时文件、dedup 命中不删共享文件；`upload_failure_after_dedup_hit_keeps_shared_file` 反证有效。

### 5.2 N+1 查询批处理（P1-6）

- **`reverse/service.py::list_history`**：原先每行走 1–2 次查询（limit=100 ⇒ 200+ 次）。改为 `_stale_reasons(rows)` 一次预取：
  - 上传缓存经文件系统判定（0 SQL）；
  - 图片存在性一次 `IN` 查询（1 SQL）；
  - 同源已完成任务的「被取代」判定纯函数 `_scan_superseded`（顺序无关，0 SQL）。
  - **结果**：100 条历史由 **201 次 → 2 次 SQL**（`test_list_history_query_count_is_constant` 断言 ≤4 且不随数量增长）。
- **`promptlib/learning.py::_find_near_duplicate`**：原先每个 segment 查 3 次。引入 `_NearDupIndex`，按 `(media_type, dimension)` 缓存候选，**每个 batch 只加载一次**；批内新增 / 合并经 `register()` 让后续 segment 立即可见。
  - **结果**：40 个 segment / 800 条目由 **240 次 → 162 次 SQL**（`loads==1` 锁证）。注：该优化减少的是重复 DB 加载，相似度比对次数另议。
- **验证**：`tests/py/test_reverse_stale.py`（10 项，含 legacy 基线等价）、`tests/py/test_prompt_learning.py`（含 `test_intra_batch_near_duplicate_merges_into_first` 锁 `register()`）。

### 5.3 流式 PNG 文本块解析（P1-8）

- **问题**：`core/imagemeta.py` 为解析 PNG 文本块（`tEXt/iTXt/zTXt`）把整图 `read_bytes()` 读进内存（ComfyUI 产出常 20–50MB），同步扫描每张图都调一次。
- **修复**：`read_png_text_chunks` 改为按 64KB chunk 顺序流式读取，仅缓冲文本块，`_skip_bytes` 用 `seek` 跳过 IDAT（大图数据）永不入内存；命中 `IEND` 即停。
  - **真实 bug 修复**：缺 IDAT 的畸形 PNG 原被 Pillow 抛 `IndexError`（未捕获 ⇒ 500）；现 `validate_image_file` 统一 `except Exception` 记 `image_verify_rejected` 并返回 `invalid_image`。
- **验证**：`tests/py/test_imagemeta.py`（24 项）。实测 5.4GB 图库、2697 PNG（最大 24.5MB），文本块均在前 1.85% 内；24.5MB 文件实际仅读 5.6KB，峰值内存 24MB→8.6KB；80 张真实图与旧全量读取器 0 不一致。

### 5.4 安全与事务（来自 `OPTIMIZATION_REVIEW` P0，已落地）

- **路径穿越（P0-1）**：`sync/paths.py::safe_join()` 为唯一实现，拒绝 `..` / 绝对路径 / 盘符，并用 `is_relative_to` 做边界判断；`workflow_file_analysis` 改用它（已修复 `../workflows-evil/secret.json` 有限任意文件读）。
- **假事务（P0-2）**：`core/db.py::tx()` 用线程局部深度计数 `_local.tx_depth`，嵌套只有最外层收口，`execute()` 在事务内不自提交；`set_default()` 两步失败可回滚。

### 5.5 整体打磨轮：易用性 / 可靠性 / 功能扩展（本轮）

## 6. 安全设计

- **路径穿越**：已实现 `safe_join` 边界判定；前端深链不泄露 `root:`。
- **SQL 注入**：无。所有 f-string 拼接只针对白名单（`_ORDER_BY` 查表、列名常量），用户输入一律 `?` 占位符。
- **密钥**：无硬编码；`OPENAI_VISION_API_KEY` / `AI_PROVIDER_API_KEY` 来自 `.env`（已在 `.gitignore`）。
- **CORS**：仅白名单放行（默认仅 ComfyUI 来源），未命中的来源不写任何 CORS 头；支持 `*` 但仅建议本机可信环境。
- **隐私 / 日志**：禁止提示词正文、图片内容、Key、完整 endpoint、绝对路径；只允许 ID / `media_type` / `dimension` / `provider` / `profile` / `stage` / `status` / `error_code` / `duration_ms` / 长度 / 字节数与尺寸。上传文件只存受控相对引用 `uploads/<hash>.png`。
- **XSS**：96 处 `innerHTML` 仅清空或注入可信 SVG（`AIBAR.icons.get()`），用户数据走 `textContent`。
